The 3D Chaotic Refractive Cipher

A detailed explanation of how the cipher works, what was wrong with the first plan, and how the C implementation will be built. Every interactive demo on this page runs locally in your browser.

Read this first: this is an educational / research cipher. It is a good way to learn about optics, fixed-point math, chaos and cryptanalysis. However, nobody can prove a homemade cipher secure by running their own tests on it. Protect real data with AES-256-GCM or ChaCha20-Poly1305.

1. The big idea

Picture a glass cube built from thousands of tiny blocks. Each block is made of a different kind of glass, so each one bends light by a different amount. The pattern of blocks is the secret. It is grown from your 256-bit key, and only someone holding the key can rebuild the same cube.

Shine a laser into the cube at a position and angle chosen by your data. The beam bends at every block boundary (refraction). It sometimes bounces back off a boundary (total internal reflection) and comes out somewhere unpredictable. If you don't know the cube, you can't predict where it comes out. That unpredictability is what we turn into a cipher.

secret key→ grow a secret 3D crystal→ data picks entry point + angle→ ray bends / bounces→ exit state → scrambled bits

On its own, "where the ray comes out" makes a weak cipher (section 2 explains why). So in the final design the ray tracer is just one component, a round function, placed inside a well-understood cipher structure (a Feistel network) that guarantees exact decryption and spreads every input bit across the whole output.

2. Problems found in the original plan

The original plan contained good ideas, but several parts would either fail to work or be easy to break. Each problem is listed below with its fix.

#ProblemWhy it mattersFix
1Q16.16 range is wrong. The plan says [100000, 241700] stands for 1.00000–2.41700. Those are decimal-scaled numbers (×100000). In Q16.16, 1.0 = 65536, so 100000 actually means ≈1.526 and 241700 means ≈3.688. Store n in [65536, 158401], which is 1.0 to 2.417 in Q16.16 (section 5).
2Encrypting one byte per ray is a lookup table. With a fixed key, byte 0x41 always produces the same exit. There are only 256 possible bytes, so an attacker who can encrypt 256 chosen bytes learns the entire cipher. The chaos in the crystal doesn't help. Encrypt 128-bit blocks through a 16-round Feistel network that uses the tracer as its round function (section 9).
3Decryption by tracing the ray backwards. Optical reversibility holds for real numbers. Fixed-point math rounds at every sqrt and every renormalization, so the backward ray drifts off the forward path. Two different inputs can also round to the same exit, and then decryption is impossible. A Feistel network can be decrypted exactly even when F cannot be inverted. You run the same F with the round keys in reverse order.
4"Snell's law is linear." It isn't. It involves a square root and a branch (refract vs reflect). The real weakness is #2: the mapping is fixed for a given key and has a tiny input space. Keep the S-box, but as extra confusion inside F, not as a cure for "linearity".
5The "CBC" step XORs the output with Ci−1 after encryption. Ci−1 is public, so anyone can XOR it back out. The step adds nothing. With no IV, encrypting the same message twice also gives the same ciphertext. Use CTR mode with a random nonce for every message (section 10).
6The ciphertext is (x, y, z, θ, φ) for every byte. That turns 1 byte into about 20 bytes, and it hands the attacker raw geometry about the secret crystal. The ray state stays internal and is compressed into output bits. Ciphertext size = message + 12-byte nonce + 32-byte tag.
7No integrity check. An attacker can flip ciphertext bits and the matching plaintext bits silently flip too. Encrypt-then-MAC with HMAC-SHA256. The tag is checked before anything is decrypted.
8Relying on chaos for security. Chaotic systems simulated in finite precision eventually fall into short repeating cycles. Many published chaos ciphers have been broken. Chaos only shapes the crystal. The secret randomness comes from HKDF-SHA256, which is mixed into every cell.
9"Post-quantum guarantees." Nothing in the design proves this. A 256-bit key gives about 128-bit security against Grover's algorithm, the same as AES-256, and no more. Drop the claim.
10The SAC test compares "Hello" with "Hello!". Those differ by an appended byte, not by one bit. "Exactly 50%" is also the wrong target, because random outputs hover around 50%. Flip one bit at a time over thousands of trials. Check that the mean is ≈50% with a small spread, and build a per-bit SAC matrix.
11Entropy > 7.999 is the pass condition. Even trivially broken ciphers (an LCG, or XOR with a repeated key on random data) can score that high. Add chi-square, serial-correlation and runs tests, and optionally the NIST STS, dieharder or PractRand suites. Treat a pass as a sanity check, not as proof of security.
12Data-dependent bounce count. When the number of steps depends on secret data, the running time leaks it (a timing side channel). Use a fixed number of boundary crossings per call, with the refract/reflect choice made by branchless selection.
13The tech stack is C++ only (templates, gtest, matplotlib-cpp). You want plain C. Your compiler (MinGW GCC 6.3) supports C11 but not C23. C11, a Makefile, a small built-in test harness, CSV output with a Python plot script, and no SIMD in version 1.

3. Final architecture

 256-bit key ──► HKDF-SHA256 ──┬─► grid seed ──► 4D hyperchaotic map ⊕ HKDF stream ──► crystal N[16][16][16]  (Q16.16)
                               ├─► S-box seed ──► key-dependent 8-bit permutation
                               ├─► 16 round keys (64-bit each)
                               └─► MAC key (256-bit)

 ENCRYPT(message):
   nonce ← 12 random bytes
   for each 16-byte block i:
       keystream_i = FEISTEL16( nonce ‖ counter_i )        ← F = 3D ray tracer
       C_i         = P_i ⊕ keystream_i
   tag = HMAC-SHA256(MAC key, nonce ‖ C)
   output: "RFC1" ‖ nonce ‖ C ‖ tag

 DECRYPT: verify tag first (reject if wrong) → regenerate the same keystream → XOR.

Notice that with CTR mode, decryption never runs the Feistel network backwards. It just generates the same keystream again. The Feistel network is still invertible, and the test suite checks that it is, but CTR mode means we only ever need the forward direction.

4. Key schedule (HKDF-SHA256)

A single key must never be used directly for several different jobs. We derive independent subkeys from it with HKDF (RFC 5869), which is built on HMAC-SHA256:

PRK = HMAC-SHA256(salt = "refcrypt-v1", key)
OKM = HMAC(PRK, T0 ‖ info ‖ 0x01) ‖ HMAC(PRK, T1 ‖ info ‖ 0x02) ‖ …

Each job gets a different info label ("grid", "sbox", "round", "mac"), so the outputs are independent. Flipping one key bit changes every subkey completely, because SHA-256 has a strong avalanche effect. The original plan said "pass the key through HMAC-SHA256". HKDF is the standard, correct way to do that.

We write SHA-256, HMAC and HKDF ourselves in C (about 250 lines) and check them against the official test vectors (FIPS 180-4, RFC 4231, RFC 5869). That way there's no OpenSSL to install on Windows.

5. Q16.16 fixed-point arithmetic

The float and double types round slightly differently depending on the compiler, the optimization flags (fused multiply-add, x87 vs SSE) and the CPU. A cipher must produce the exact same bits everywhere, or a file encrypted on one PC won't decrypt on another. So we store every real number as an integer that counts units of 1/65536:

value = stored_int / 65536     (16 integer bits . 16 fractional bits, stored in int32_t)
Real valueQ16.16 integerHex
1.0655360x00010000
1.5983040x00018000
2.417 (diamond)1584010x00026AC1
0.5327680x00008000
−0.866025−567560xFFFF224C

The operations

add:  a + b                               (exact, same as integers)
mul:  (int32_t)(((int64_t)a * b) >> 16)   e.g. 1.5×1.5: 98304×98304 = 9663676416; >>16 = 147456 = 2.25 ✓
div:  (int32_t)(((int64_t)a << 16) / b)
sqrt: integer square root of ((int64_t)a << 16)   (bit-by-bit method, deterministic)

Every intermediate value goes through int64_t so it can't overflow. Arithmetic shifts of negative numbers are implementation-defined in C, so fixed.c handles signs explicitly.

6. The 4D hyperchaotic map & growing the crystal

The crystal is shaped by a 4-dimensional hyperchaotic Lorenz-type system:

ẋ = a(y − x) + w
ẏ = c·x − y − x·z
ż = x·y − b·z
ẇ = −y·z + r·w

The parameters often quoted in the literature are a = 10, b = 8/3, c = 28 and r ≈ −1. The C code will check these numerically, because the system is only hyperchaotic (two positive Lyapunov exponents) for certain r values. The initial values (x0, y0, z0, w0) come from the HKDF "grid" output. We integrate with fixed-point Runge-Kutta 4, discard the first 1000 steps as warm-up, and then sample the state.

Sensitivity demo: the two curves below start from initial states that differ by only 10−10. They overlap at first, then split apart completely. That is the "butterfly effect" the original plan relies on.

Building each cell

for each cell (z, y, x):
    step the chaotic system k times
    s   = low 32 bits of (x_state ⊕ w_state)      ← chaotic "shape"
    h   = next 4 bytes of HKDF("grid")            ← cryptographic randomness
    u   = s ⊕ h                                   ← even if the chaos cycles, h keeps cells unpredictable
    N[z][y][x] = 65536 + (u mod 92866)            ← maps into [1.0, 2.417] in Q16.16
Why XOR in HKDF bytes? (Issue 8.) Chaotic orbits simulated with fixed-point numbers have a finite number of states, so they must eventually repeat, sometimes after only a few thousand steps. XOR-ing in HKDF output means that even if the chaos turns out to be weak, the crystal is still as unpredictable as SHA-256 output.

7. Snell's law & total internal reflection (vector form)

When a ray crosses from glass of index n1 into glass of index n2, it bends according to Snell's law, n1 sin θ1 = n2 sin θ2. In 3D it is easier and faster to use the vector form, which needs no sin, cos or arcsin:

r = n1 / n2,    c1 = −N·I,    k = 1 − r²(1 − c1²)
if k ≥ 0 (refract):   R = r·I + (r·c1 − √k)·N
if k < 0 (TIR):         R = I + 2c1·N

Here I is the unit direction of the incoming ray and N is the unit surface normal, pointing back toward the side the ray comes from. The crystal is made of cubes, so N is always an axis vector such as (±1,0,0), and the dot product just picks out one component. Total internal reflection happens when the ray goes from dense to less dense glass (n1 > n2) at an angle steeper than the critical angle θc = arcsin(n2/n1).

Worked example

n1 = 1.5, n2 = 1.0, angle of incidence 30°, interface horizontal, so N = (0, 1) and I = (sin 30°, −cos 30°) = (0.5, −0.8660).

r  = 1.5 / 1.0                    = 1.5
c1 = −N·I = −(0·0.5 + 1·(−0.8660)) = 0.8660
k  = 1 − 1.5² · (1 − 0.8660²)      = 1 − 2.25 · 0.25 = 0.4375   (≥ 0 → refracts)
√k                                 = 0.6614
R  = 1.5·(0.5, −0.8660) + (1.5·0.8660 − 0.6614)·(0, 1)
   = (0.75, −1.2990) + (0, 0.6376) = (0.75, −0.6614)
|R| = √(0.5625 + 0.4375) = 1  ✓   exit angle = arcsin(0.75) = 48.59°  ✓ (Snell: 1.5·sin30° = 0.75)

Raise the angle to 50° and you get k = 1 − 2.25·(1 − 0.6428²) = −0.320 < 0, so TIR. The critical angle here is arcsin(1/1.5) = 41.81°.

8. Tracing a ray through a crystal

The real cipher uses a 16×16×16 crystal. To keep the picture readable, this demo uses a 16×16 slice in 2D. The demo also uses a toy PRNG instead of HKDF+chaos and floating point instead of Q16.16. The ray logic is otherwise the same as the C version:

  1. Entry: the 16-bit input (already XOR-ed with the round key) chooses the entry column (low byte) and the entry angle (high byte, −60° to +60°).
  2. Voxel walk (DDA): find the nearest cell boundary along the ray and move to it.
  3. At the boundary: read n1 (current cell) and n2 (next cell), then apply Snell or TIR as in section 7. At the outer walls of the crystal the ray reflects like a mirror.
  4. S-box mixing: at each crossing, the cell index goes through the key-dependent S-box and is mixed into a running 32-bit accumulator, along with whether the event was a refraction or a TIR.
  5. Fixed step count: always exactly 32 crossings, so the running time doesn't depend on the data (issue 12).
  6. Output: the accumulator, final position and final direction are hashed down to the round-function output.

Click input + 1 a few times. A one-unit change in the input moves the entry point or angle slightly, and after a few boundary crossings the path is completely different. Change one character of the key and the whole crystal changes. Blue/white dots are refractions, red dots are total internal reflections and orange dots are wall bounces.

Being honest about who does what: the optics supply a key-dependent, nonlinear, branching path through secret data. Much of the bit-level diffusion comes from the S-box and the final mixing hash. The attack suite (section 11) measures how much each part contributes, including a test with the optics disabled.

9. The Feistel network: why decryption is always exact

A Feistel network splits a block into a left half L and a right half R and repeats this round:

Li+1 = Ri      Ri+1 = Li ⊕ F(Ri, Ki)

Here's the key trick. Given the outputs (Li+1, Ri+1), we can recover the inputs:

Ri = Li+1      Li = Ri+1 ⊕ F(Li+1, Ki)

Decryption only ever calls F forwards, on a value we already have. F doesn't need to be invertible, so it can round, branch, collapse two inputs into one, or do anything else. That is why the fixed-point ray tracer can serve as F, even though tracing it backwards would fail (issue 3). This is the same structure DES used, and Luby and Rackoff proved that with 4 or more rounds of a good pseudorandom F it gives a pseudorandom permutation. We use 16 rounds for a safety margin.

10. CTR mode + HMAC (how real files get encrypted)

A block cipher on its own handles only 16 bytes, and it always maps the same input to the same output. A mode of operation fixes both problems:

nonce (12 random bytes, new for EVERY message)

block 0:  FEISTEL16( nonce ‖ 00000000 ) ──► keystream₀ ──⊕── P₀ ──► C₀
block 1:  FEISTEL16( nonce ‖ 00000001 ) ──► keystream₁ ──⊕── P₁ ──► C₁
block 2:  FEISTEL16( nonce ‖ 00000002 ) ──► keystream₂ ──⊕── P₂ ──► C₂   (last block may be partial: no padding needed)

tag = HMAC-SHA256( mac_key, "RFC1" ‖ nonce ‖ C₀ ‖ C₁ ‖ … )
  • Why the nonce: encrypting the same file twice gives completely different ciphertexts, so an attacker can't tell that two messages are identical. Never reuse a nonce with the same key. If you do, C ⊕ C′ = P ⊕ P′ and the keystream cancels out.
  • Why HMAC (encrypt-then-MAC): without it, flipping bit j of the ciphertext flips bit j of the decrypted plaintext, and nobody notices. With HMAC, decryption first recomputes the tag. If even one bit was altered, it refuses to output anything. The comparison runs in constant time.
  • Why a separate MAC key: HKDF gives the MAC its own key, so a weakness in the ray-tracing part can't be turned against the authentication.

File format: "RFC1" (4 bytes) ‖ nonce (12) ‖ ciphertext (same length as the plaintext) ‖ tag (32), so the overhead is a fixed 48 bytes.

11. The automated attack suite

A second program, attack.exe, tries to break the cipher. Each test targets a specific weakness:

11.1 Strict Avalanche Criterion (SAC) / differential test

Pick a random block X. For each input bit i, flip it to get X′, then compare E(X) with E(X′). If the cipher is good, every output bit j flips with probability ½, independently of i.

  • Mean avalanche over thousands of trials should be ≈ 50% (for 128-bit blocks, about 64 ± 5.7 bits per trial).
  • SAC matrix M[i][j] = fraction of trials where flipping input bit i flipped output bit j. Every entry should be ≈ 0.5. A cell near 0 or 1 is a differential characteristic, a crack an attacker can use.
  • We run this on F alone, on 1, 2, 4 and 16 Feistel rounds, and on key bits as well as plaintext bits. This shows how many rounds it takes to reach full diffusion.

11.2 Impulse-response / linearity test

Encrypt the all-zero block and every "single 1-bit" block (0x…01, 0x…02, …). If the cipher were linear over GF(2), then E(a ⊕ b) = E(a) ⊕ E(b) ⊕ E(0) would hold, and the 128 impulse responses would describe the whole cipher. The test checks this equation on random pairs (a, b). For a nonlinear cipher it should hold about as often as chance, roughly 2−128, which in practice means never.

11.3 Known-plaintext codebook attack (proving the redesign was needed)

We deliberately build the original design (one byte per ray, no Feistel, no nonce), encrypt all 256 bytes once, and record a table. With that table the attack decrypts any message encrypted under the same key. This attack must succeed against the weak variant and must fail against the real cipher. Showing that both happen is how we know the attack suite actually works.

To feed external suites (NIST STS, dieharder, PractRand), the C program can also write raw keystream to a file or to stdout.

Passing all of these does not make the cipher secure. These tests catch obvious flaws. Real cryptanalysis (linear and differential trails, related-key, slide and algebraic attacks) needs expert review over many years. That is why AES and ChaCha20 are trusted and new designs are not.

12. Limitations & honest caveats

  • Speed: one call to F is a 32-step voxel walk with fixed-point sqrt, and there are 16 rounds per block. Expect this to be 100–1000× slower than AES. That's fine for learning, but not for bulk data.
  • Side channels: cache timing from table lookups (the S-box and grid reads depend on secret data) is not eliminated.
  • The chaos map is decorative for security, because HKDF provides the real randomness. It still makes the crystal structure interesting, and it can be analysed on its own (cycle length, Lyapunov exponents).
  • No security proof, and no third-party analysis.
